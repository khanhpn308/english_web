## Context

T086 đã đưa ba read-only reviewer perspectives vào cùng một task và chứng minh reviewer calls overlap thật.

Workflow hiện tại vẫn tuần tự ở cấp phase:

Worker -> executable verification -> parallel reviewers -> authoritative Auditor.

Current `verify()` mutates RunState/artifact authority after each command. Current `parallel_review()` also performs parent state/artifact management and requires an existing `audit_checks` artifact. Therefore these two existing methods MUST NOT simply be called concurrently.

Observed local evidence after T086 integration:

- portable Python suite alone: 1063 passed in 88.54 s; wall-clock 89.2 s;
- `check:task:portable` observed about 99–107 s;
- portable pytest is the dominant gate under concurrent Phase-A load.

T087 aims to hide verification latency behind remote reviewer inference without weakening or skipping any verification.

## Required behavior

### 1. Concurrent audit preparation

After Worker/Fix Worker reaches `IMPLEMENTED` and the source is frozen, launch concurrently:

- one executable verification lane;
- all three T086 reviewer shards.

The verification lane itself keeps command order deterministic.

T087 does not parallelize individual verification commands beyond concurrency already implemented by repository scripts such as pytest-xdist and `run-gates.sh`.

### 2. Do not run mutable `verify()` concurrently

Current `Pipeline.verify()` mutates RunState, artifacts and `state.json`.

Do NOT submit the existing mutable `verify()` method into a thread executor beside review calls.

Introduce a verification collection primitive or equivalent which:

- receives immutable inputs;
- runs executable commands;
- does not receive mutable RunState;
- does not call `save()`;
- does not call `artifact()`;
- does not register authoritative artifacts;
- returns deterministic verification evidence to the joining parent.

Only the parent may persist/register `audit_checks`.

### 3. Do not call `Pipeline.invoke()` concurrently

T086 rule remains mandatory.

Reviewer threads call the configured provider through the dedicated read-only path.

Authoritative Auditor uses normal `Pipeline.invoke()` only after concurrent audit preparation has completely joined.

### 4. Freeze before dispatch

Before either lane starts, parent must validate and freeze at minimum:

- contract;
- task/run authoritative artifacts;
- Git source digest;
- worktree branch;
- relevant skill manifest;
- parent RunState.

All reviewer prompts must be prepared before dispatch.

### 5. Reviewer context is static

Reviewer shards run concurrently with executable verification and therefore MUST NOT depend on unfinished `audit_checks`.

Reviewer prompts may inspect:

- frozen source;
- contract;
- Worker result;
- task context;
- applicable skills.

They must not claim or infer executable test PASS/FAIL.

Transient files generated by verification are non-authoritative reviewer evidence.

Final Auditor alone receives completed executable evidence.

### 6. Parent-only authority

During concurrent lanes:

- no thread mutates authoritative RunState;
- no thread registers authoritative artifacts;
- no thread transitions state;
- no reviewer edits source.

After all futures are reaped and invariants revalidated, parent alone may:

1. persist/register executable evidence;
2. persist/register reviewer diagnostics;
3. assemble/register deterministic ReviewBundle;
4. clear concurrent-phase state;
5. invoke authoritative Auditor.

### 7. Verification semantics remain compatible

Preserve existing audit verification semantics.

A normal verification regression such as:

- nonzero exit code;
- timeout;
- oversized result;

must produce executable evidence and mark checks as failed.

Reviewers must still be reaped.

Authoritative Auditor may still run so it can produce the normal FAIL report.

Python must continue forbidding PASS when executable evidence failed.

A setup/infrastructure exception which currently represents `SETUP_FAILED` remains fatal and must not be converted into an ordinary task regression.

### 8. Failure aggregation

All started verification/reviewer futures must be reaped before leaving the concurrent phase.

Required fail-closed cases include:

- reviewer process/schema/output failure;
- reviewer wrong perspective;
- verification setup failure;
- source mutation;
- branch mutation;
- authoritative state/artifact mutation.

No incomplete ReviewBundle may be passed to final Auditor.

### 9. Deterministic evidence

Reviewer completion order must not affect:

- perspective order;
- finding IDs;
- ReviewBundle ordering.

Verification command results must remain in contract/config declaration order.

Concurrency timing must not affect semantic artifact ordering.

### 10. Source integrity

Verification and reviewers operate against the same frozen Git source digest.

After joining, parent must verify that tracked source and branch remain unchanged.

Generated ignored coverage/build/test output is not authoritative source evidence and must not be treated as reviewer evidence.

### 11. Final Auditor barrier

The authoritative Auditor MUST NOT start until:

- verification lane has completed;
- every required reviewer has completed;
- all futures have been reaped;
- source/branch/state/artifact invariants pass;
- `audit_checks` is authoritative;
- complete ReviewBundle is authoritative.

Final Auditor receives both complete inputs.

### 12. Preserve T086 semantics

Do not regress:

- three required reviewer perspectives;
- true reviewer-reviewer overlap;
- deterministic host finding IDs;
- reviewer disposition rules;
- historical Audit compatibility;
- single-writer invariant;
- bounded final Audit correction retries.

### 13. Preserve surrounding orchestration

Do not change:

- T084 portable gate commands or thresholds;
- T085 dependency parsing;
- Level 2 scheduler behavior;
- scheduler max_workers;
- runtime admission slots;
- retry provenance;
- integration semantics;
- `max_fix_cycles`;
- provider/model defaults.
