## UXR-02A handoff and extension seams

The shared contract must specify one primary action, two information levels, content-driven metric sizing, one entire-history empty state, contextual mixed-data empties, correct zero/null/unknown/degraded labels, and narrow/zoom reachability. Density cannot reduce consent disclosure, error reasons, answer area, verification labels or control usability. Define the common components before independent feature redesign; otherwise each screen will recreate card density and status treatment.

Recommended mockup order: G1 grouped navigation/content-header variations; G9 first-run and populated compact layouts; G8 readiness/consent-first and diagnostics expansion; then feature designs using the same contract. UXR-01 can explore direction based on source findings and A3 evidence. Owner direction and compact Dashboard approval remain required before dependent UXR-03–09 design work; A2 does not confer that approval.

Future extension mapping is conceptual only:

| Seam | Design requirement now | Implementation boundary |
|---|---|---|
| Navigation | Static feature-group descriptor concept with `featureId`, section, route, capabilities, enabled and order. Existing Vocabulary/Practice/System items work; Library/book exercise/book progress slots remain hidden until enabled. | Preserve current v1 routes. No blank future screens, dynamic plugins, new router, sidebar shortcut mandate or schema change. |
| Resource contexts | Shared ResourceHeader and Breadcrumb language can later display edition, source/license and typed skill/framework chips. | No book metadata/tags are inferred for current word forms; ISBN/publisher data and reader formats need separate scoped work. |
| Exercise surface | Shared shell/tokens plus distinct focused runner layout; reusable status/progress/autosave presentation. | Vocabulary quiz immutable attempt and self-score semantics stay intact; future book exercise contract is separate. |
| Progress | Additional future widgets use known numerator/denominator and explicit completion source. | Keep book reading position, completion, exercise performance, vocabulary SRS/streak and objective/self/AI measures separate. No invented IELTS/CEFR certification, mastery or chart trend. |
| Primitive maintenance | One canonical `components/ui` source set, app compositions free of HTTP/SQLite, feature containers retaining state machines. | No indiscriminate Base UI/Radix mixing, unscoped package upgrade, wholesale CSS scaffold or third-party registry. |

## Official source comparison (retrieved 12/10/2026)

1. **Foundation fits current guidance.** Existing `new-york`, `tsx: true`, `rsc: false`, CSS variables, Tailwind v4 blank config and aliases correspond to documented configuration. The docs support existing-project setup; foundation reinstall is unnecessary. [components.json](https://ui.shadcn.com/docs/components-json), [Vite existing project](https://ui.shadcn.com/docs/installation/vite#existing-project).
2. **Explicit primitive flavor matters.** Generic component URLs currently redirect to Base UI pages. The Radix Sidebar page explicitly exposes alternative flavors, grouped/menu composition, controlled open/mobile state, anchor composition and active-state prop. Use `/docs/components/radix/...` references for this existing Radix app; retain native semantics and verify pinned generated dependencies. The official example's default shortcut is not a product requirement. [Radix Sidebar](https://ui.shadcn.com/docs/components/radix/sidebar).
3. **Tokens permit a custom academic visual direction.** Official theming recommends semantic CSS-variable surface/foreground pairs and central radius. Existing tokens can be adjusted in an approved foundation task without restyling every feature. Latest theme page examples use a different style/radius scaffold; configuration page still documents `new-york`. This documentation difference is not evidence the current app needs regeneration. [Theming](https://ui.shadcn.com/docs/theming), [configuration style](https://ui.shadcn.com/docs/components-json#style).
4. **Source ownership supports scoped maintenance.** Official introduction describes open component code and composition; it does not prescribe one aesthetic or give automatic application accessibility certification. App obligations and evidence survive component adoption. [Introduction](https://ui.shadcn.com/docs).
5. **Dry-run/diff guidance is verified, not executed.** Current CLI reference documents `--dry-run`, `--diff [path]`, `--view [path]`, overwrite and all options. Repository strategy appropriately requires scoped/pinned review rather than blanket add/overwrite; no CLI was run by A2. [CLI](https://ui.shadcn.com/docs/cli#add).
