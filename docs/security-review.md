# Security review — Vocabulary learning app

**Status:** Planning baseline — release verification required  
**Date:** 29/09/2026 (`Asia/Bangkok`)  
**Scope:** local Windows process, browser UI, Markdown files, SQLite, local OpenAI-compatible bridge and cloud inference behind that bridge.

This is a threat model, not a claim that security controls already exist. The most important trust boundaries are: browser → API, API → local filesystem, API → SQLite, API → bridge, bridge → cloud provider, and external Markdown/LLM output → application logic.

The product has no app account, password, multi-user role, LAN access, cloud sync or in-app backup. Per the owner's accepted [ADR-0002](adr/0002-antigravity-loopback-trust-boundary.md), the Windows host/account is the bridge trust boundary. Malicious local proxy impersonation is an explicitly accepted residual risk, not prevented by loopback + client API key. Browser session/CSRF and file protections remain required; threat severity is not lowered by accepting this residual. AI cloud sharing is separately gated by [ADR-0003](adr/0003-ai-consent-and-revocation.md): no current consent/policy means no new cloud dispatch.

## 2. Security decisions and trade-offs

### Local session without a product login

The spec explicitly excludes accounts and passwords. A loopback bind alone does not stop another local process, so the launcher should open a fragment token, exchange it once by POST through a trusted bootstrap page, immediately replace the browser URL before loading the main app, and set an `HttpOnly; SameSite=Strict` cookie without exposing the token to application components. This reduces accidental and cross-origin access while retaining the product's no-login experience. Local HTTP cannot honestly claim the `Secure` cookie attribute; the residual risk is limited by loopback binding and the OS trust boundary. TTL, restart, second-tab and single-instance behavior follow ADR-0004 and the launcher runbook.

### Data and cloud boundary

The local database is canonical for history, SRS and quiz state. The client-key-authenticated bridge receives only task-scoped payloads. ADR-0004 fixes the v1 provider/model/default-fallback and explicit provider-controlled retention/region disclosure; the app still cannot guarantee provider terms or make inference private/free. Keep correlation in app logs/spans and strip app diagnostic headers before entering Antigravity; proxy-generated metadata/logs remain outside the app's guarantees.

**Consent boundary (29/09/2026):** Owner-approved [ADR-0003](adr/0003-ai-consent-and-revocation.md) requires explicit consent before lookup, AI quiz generation or writing feedback. Consent is a local permission record, not provider approval: the v1 READY policy in ADR-0004 identifies the approved scopes/recipient/model/route/billing and discloses provider-controlled retention/region. Backend default-denies and rechecks consent/policy immediately before dispatch; revoke works without bridge/network. It cannot recall bytes already handed to an in-flight transport or delete third-party copies. Consent never authorizes audio or telemetry export. Paid fallback is not enabled by default and requires a new policy version/digest plus fresh consent.

**Accepted boundary (29/09/2026):** Antigravity v4.8.4 at the exact HTTP loopback origin, `allow_lan_access=false`, `auth_mode=all_except_health`, mandatory client key, distinct admin password and backend-only credential handling are documented in ADR-0002/API §6. `auto` resolves to `off` for local-only mode in the inspected version, so it is not the approved profile. The app uses only a proxy key, never Google tokens/sessions or admin credentials. Preflight checks do not establish server identity. The owner explicitly accepted local impersonation risk in place of the prior process-authentication/IPC requirement. R2-001 and R2-002 are addressed at the design level by ADR-0002/0004; implementation/profile and policy-fixture verification are still required. Sources and verification cases are linked from ADR-0002/0004; this is not security sign-off.

### Markdown safety

Markdown is a user-controlled source, not executable code. The parser stores normalized fields and source metadata; the renderer must not trust raw HTML. Invalid or missing files are quarantined from active study and are read-only until repair/relink is explicitly supported; history remains queryable. Legacy filename formats and unknown/context fields require lossless round-trip fixtures before writes are enabled.

### LLM safety

LLM output is untrusted input. It can be stored only after schema validation and may never become SQL, a shell command, DOM HTML, a path or an automatic final writing score. The system prompt/template is not an authorization boundary; code-level allowlists are.

## 3. Security headers and transport

The local FastAPI response should set a restrictive baseline: `Content-Security-Policy` (`default-src 'self'`; connect only to same-origin API), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` for bootstrap/status/diagnostic responses, `X-Frame-Options: DENY`/`frame-ancestors 'none'`, and a strict `Permissions-Policy`. HSTS is not applicable to plain loopback HTTP and must not be falsely enabled; if HTTPS is introduced, document certificate/key handling separately. Local SpeechSynthesis uses no remote `media-src`.

Do not add permissive CORS “for development” to the shipped process. Vite's development server may use a narrowly configured proxy, but production UI and API are same-origin.

## 4. Verification gate

Before implementation is considered security-ready:

1. Threat tests above pass with a fake bridge and hostile fixtures.
2. Browser DevTools confirms headers, same-origin behavior and no credential in frontend bundles.
3. Native package audits show no unmitigated reachable critical/high finding; dependency scripts are reviewed.
4. Secret scan passes for the staged diff and history check confirms any previously exposed bridge key was rotated.
5. A local failure can be traced by request ID without logging the prompt, answer, token or full response.
6. Verify ADR-0004's provider/default-fallback, SRS, source journal, launcher, accessibility, benchmark, audio and recovery requirements, plus `BR-AUTH-01`–`09` and `CONSENT-01`–`12`, before release. These are implementation evidence gates, not unresolved product questions; no acceptance is a passed runtime/security test.
